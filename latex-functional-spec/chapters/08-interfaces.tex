\subsection{Operations view (E12)}
Operators see request, error and latency rates, queue depth and oldest-job age, worker failures and retries, dependency health, model and retrieval signals, and voice signals. They can follow a single trace ID across modules.

\section{External interfaces}
\subsection{Model provider}
Conceptual interface kept behind an adapter:
\begin{itemize}
  \item \code{generate_response(input, output_schema, options)}
  \item \code{stream_response(input, options)}
  \item \code{classify(input, taxonomy, options)}
  \item \code{embed(texts, model_configuration)}
  \item optional \code{open_realtime_session(configuration)}
\end{itemize}
Vendor-specific request and response shapes stay in adapters. Model name and version, latency, usage and provider errors are captured without storing secrets.

\subsection{Speech provider (R2)}
Two strategies are supported behind a common abstraction. \textbf{Option A}: modular pipeline audio $\rightarrow$ STT $\rightarrow$ conversation engine $\rightarrow$ TTS $\rightarrow$ audio (explicit transcript, modular provider choice, more latency). \textbf{Option B}: speech-to-speech with a real-time multimodal model (potentially more natural, but more provider coupling). One strategy is started first, chosen on latency, language, cost and observability.

\subsection{Channel providers and webhooks}
Webhook handling follows eight steps:
\begin{enumerate}
  \item verify the provider signature and timestamp;
  \item resolve the channel or integration from trusted endpoint configuration;
  \item enforce body-size and schema limits;
  \item persist the event ID and the payload or minimal normalized data;
  \item return success only after durable acceptance;
  \item process asynchronously;
  \item deduplicate provider retries;
  \item record processing state and failure reason without leaking secrets.
\end{enumerate}

\subsection{Business tools and connectors}
Tool integration has three layers: the \emph{tool definition} (what the AI may request), the \emph{tool execution service} (validation, authorization, idempotency, audit, timeout, result normalization) and the \emph{connector adapter} (provider-specific authentication and mapping). The AI never receives raw credentials.

\begin{table}[htbp]
\centering\caption{Fields of a tool definition}\label{tab:toolfields}
\begin{tabular}{@{}p{4.5cm}p{11.5cm}@{}}
\toprule \textbf{Field} & \textbf{Description} \\ \midrule
Stable name and description & For example \code{orders.lookup}. \\

Allowed scope & Agents and tenants permitted to use the tool. \\

\end{tabular}
\end{table}

\noindent Example contract for the MVP read-only tool (illustrative, not a claim about any commerce provider):
\begin{encadre}{\code{orders.lookup}, version 1, risk: read-only}
\textbf{Input:} \code{order_reference} (string, 3 to 80 characters), required, no additional properties.\\
\textbf{Output:} \code{status} (string) and \code{estimated_delivery} (string or null), both required, no additional properties.
\end{encadre}

\noindent Connector failures are mapped to the categories: \code{AUTHENTICATION_FAILED}, \code{AUTHORIZATION_DENIED}, \code{NOT_FOUND}, \code{VALIDATION_FAILED}, \code{RATE_LIMITED}, \code{TIMEOUT}, \code{PROVIDER_UNAVAILABLE}, \code{CONFLICT}, \code{UNKNOWN_OUTCOME}. Only safe-to-retry failures are retried.

\section{Internal event contracts}
Modules communicate through synchronous interfaces and asynchronous events. Every event and request carries \code{trace_id}, \code{correlation_id}, \code{causation_id}, \code{tenant_id}, and where relevant \code{conversation_id}, \code{turn_id}, \code{tool_execution_id} and \code{provider_request_id}. Message text, e-mail, phone numbers and tokens never appear in metric labels.
