\chapter{Technology Stack and Choices}

\section{Status and how to read this}

This document proposes the technologies for the AI Customer Support Platform. It is a \textbf{recommendation, not a decision}. Each choice is confirmed or replaced through the architecture decision records (ADRs) listed in the release plan. Where a provider or product is named, it is an example of a category, and the product docs already require that provider-specific details live in adapters, not in the core domain.

Vendor names, versions, prices, licenses and data policies change. Verify them at the time of each ADR.

\section{Selection criteria}

\begin{enumerate}
\item \textbf{Fit for a small team and a modular monolith.} Few moving parts, one primary language, one primary database.
\item \textbf{Proven and boring where it matters.} Use mature tools for storage, queues, auth and delivery. Spend novelty budget on the AI behavior.
\item \textbf{Security and tenant isolation first.} The technology must make cross-tenant access hard, not just unlikely.
\item \textbf{Portable at the core.} No LLM, speech, channel or cloud vendor type appears in the domain.
\item \textbf{Observable and testable.} Every important decision, tool call and failure can be traced and replayed in tests.
\item \textbf{Reasonable cost.} Start on the simplest option that meets the requirement and keep a documented trigger for moving up.
\end{enumerate}
\section{Assumptions}

\begin{itemize}
\item A small team, text MVP first, voice and operations later.
\item TypeScript is the primary language. If the team prefers Python, the rows marked ``language'' change and the architecture does not.
\item Cloud-agnostic containers. Managed services are fine, but no design depends on one cloud.
\item The first release has exactly one read-only business tool and one channel (website chat).
\end{itemize}

\section{How a request flows through the stack}

A website message enters through the widget over HTTPS or WebSocket. The API validates it, checks the session token, and writes the message and an outbox row in one Postgres transaction. A worker picks up the turn job, builds context, retrieves knowledge with a tenant filter, and calls the model through the adapter. If the model proposes a tool call, the tool service validates it against its JSON Schema, checks authorization and idempotency, and calls the connector with a timeout and circuit breaker. The reply is persisted with citations and usage, then pushed to the widget. No database transaction is held open while the model or a business system is called.

\section{Voice stack}

Browser audio travels over WebRTC to a media server. Voice activity detection finds the end of speech. Streaming speech-to-text produces partial transcripts, which are captions only, and a final transcript, which becomes a message. The same conversation engine and the same tool authorization answer, and streaming text-to-speech plays the reply. A barge-in cancels the speech stream and the model call. The alternative, a speech-to-speech model, sits behind the same adapter and still routes tool calls through our authorization.
