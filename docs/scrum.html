The one sentence everything serves

Product Goal

A customer can contact an organization through website chat, receive accurate knowledge-grounded answers, complete at least one authorized read-only business lookup, and reach a human without losing context.

The architecture must be ready to add voice without duplicating business reasoning.

The Product Goal is the long-term objective. Each Sprint Goal should move us toward it.
Fit

Why Scrum suits this product

AI behaviour is uncertain

We cannot predict answer quality on paper. Each Sprint ends with a demo and an evaluation run, so we inspect real behaviour.

Vendors drive risk

Voice and business integrations depend on provider limits and credentials. Short Sprints and spikes expose that early.

Security is not a phase

Tenant isolation, authorization and privacy are inside every Definition of Done, not a final checkpoint.

Accountabilities

Three accountabilities, one team

Product Owner

  • Product value and Product Goal
  • Orders the Product Backlog
  • Accepts Sprint results

Scrum Master

  • Coaches Scrum
  • Removes impediments
  • Helps the team improve

Developers

  • Cross-functional team
  • Design, build, test, integrate
  • Secure and operate the Increment

Stakeholders: support teams, organization admins, customers, security and privacy, business-system owners. Roles may be held by a small team, but the accountabilities stay clear.

How work flows

  • Refine the Product Backlog all the time
  • Plan a Sprint: one Sprint Goal, selected items
  • Build until each item meets the Definition of Done
  • Review the Increment with stakeholders, feed learning back into the backlog
  • Retrospect and carry improvement actions into the next Sprint

Part three

Quality: ready, done, safe to ship

The agreements that keep the Increment trustworthy.

Team agreement, not a gate for discovery work

Definition of Ready

  • The user or business outcome is clear
  • Acceptance criteria are testable
  • Dependencies and provider assumptions are identified
  • UX, API and data behaviour are understood, security and privacy considered
  • Small enough for one Sprint, and estimated
  • Credentials, test data and environments are available or planned
Three layers

Definition of Done

Every item

  • Acceptance criteria met
  • Reviewed, module boundaries kept
  • Tests incl. failure cases
  • Tenant isolation and authz tested
  • Safe, redacted telemetry
  • Docs and contracts updated
  • Rollback or flag understood

AI items add

  • Model and prompt version identifiable
  • Tool permissions enforced in code
  • Retrieval tenant scoped
  • Empty and uncertain paths tested
  • Regression example added
  • No secrets or hidden reasoning in logs

Voice items add

  • Mic permission and active state clear
  • Cleanup on disconnect
  • Interruption tested
  • Transcript order tested
  • Retention per policy
  • Latency and failure metrics

A story's life

  • Candidate → Refinement → Ready: clarified until it meets the Definition of Ready
  • Selected: pulled into a Sprint at planning
  • In progress ↔ Review: changes requested send it back
  • Blocked: visible, and returns to In progress when freed
  • Done: only when the Definition of Done is met
Exit criteria

When a release may ship

Release 1
  • Tenant isolation tests pass
  • Inbound messages deduplicated
  • Safe fallback for unknown questions
  • Tools allowlisted, authorized, audited
  • A human can take over
  • API and worker telemetry available
  • No open critical evaluation failure
Release 2
  • Session start, stop, cleanup reliable
  • Transcript finalization and ordering
  • Interruption behaviour tested
  • Audio and transcript privacy implemented
  • Latency and cost metrics visible
  • Handoff validated for the chosen provider

Top risks and what we do about them

Risks and mitigations

RiskMitigation
Prompt injectionTool allowlist, server-side authorization, untrusted-content boundaries, adversarial tests
Tenant data leakageTenant-scoped indexes and filters, cross-tenant tests in CI
LLM latency and costBudgets, timeouts, model routing, measurement
Duplicate webhook or tool callDurable inbox, idempotency keys, deduplication
Voice interruption racesSequence ids, partial vs final, cancellation semantics
Unsupported AI answerEvidence thresholds, safe fallback, handoff
Provider lock-in, scope too broadAdapters and contract tests; text-MVP vertical slice first
Decide the right things at the right time

Decide now, defer on purpose

Architecture decisions to write (ADRs)

  • Modular monolith boundaries
  • Database and tenant isolation
  • Queue, outbox and inbox
  • Vector and search technology
  • LLM abstraction and data policy
  • Voice strategy, transport, retention
  • Authentication and customer verification
  • Tool authorization and approval

Do not decide yet

  • One microservice per module
  • A universal workflow builder
  • Several speech providers at once
  • Autonomous write access to every system
  • Permanent raw audio retention
  • Complex billing before usage is known
